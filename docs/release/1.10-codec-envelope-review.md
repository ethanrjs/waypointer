# Codec envelope measurements

Keep the current production envelope and compression portfolio. Searching 27 legal Java DEFLATE settings saves just **5 characters across 302 coordinate-only routes** (0.0066%). The corresponding full-fidelity and no-names savings are one character each. None of the real-route 1/2/3/5/10-point prefixes becomes shorter. This is insufficient evidence for production complexity or extra compression work.

A separate hypothetical tiny-route wire format saves roughly 1.2–1.5 characters per small route while retaining CRC-16. It requires a new version and importer support, so it is also **not recommended for this release**. No production codec or decoder was changed by this audit.

## Reproduction and scope

- Production baseline: `8e85aea3e9b847369d1c014a476f29b3d5899849`, Java 25.
- Corpus: the supplied `1-waypoints-2-.json`, 302 routes / 31,418 points.
- Corpus SHA-256: `2179ccf560c24291fa706cdbf8b89c2d36fc526560040bfa717a30675a3d21d7`.
- Every experiment uses the strict `CodecRouteCorpus` adapter. Rich profiles use its explicit RGB quantization, name normalization, and zone mapping; they make no claim of lossless serialization of the source JSON itself.
- Every reported length includes `WP:`, the actual contextual base-91 text, framing, and CRC. All output is ASCII, so the character counts also equal UTF-8 byte counts.
- Prefix results are synthetic ordered prefixes of the real routes, not independently sourced tiny routes. The `full_tiny` rows identify actual corpus routes with at most 16 points.
- The external corpus is not committed. Per-route/index baseline measurements are retained under `tools/codec-experiments/baselines/`.

With already-compiled production classes and a file containing the Java runtime classpath:

```sh
JAVA_HOME=/path/to/jdk-25 \
  bash tools/codec-experiments/run-envelope-audit.sh \
  /path/to/1-waypoints-2-.json \
  /path/to/runtime-classpath.txt \
  /tmp/waypointer-codec-envelope
```

The script compiles only experiment/test helpers, runs no Gradle command, and writes its classes and output outside production sources. It emits `results.csv`, `rich-results.csv`, and `tiny-version11-results.csv`.

The current baseline differs from the historical `V10LockedCorpusTest` total of 76,699 because that fixture predates the current packed-header envelope. This audit preserves the measured 75,674 baseline instead of silently changing the historical assertions.

## Current frame cost

V10 already combines the wire version, content kind, and transport mode in one byte. There is no independent selector, version byte, compression byte, DEFLATE wrapper, terminator, or nested text layer in a single bare route. Beyond content, its cost is:

- Three ASCII prefix characters, `WP:`.
- One transmitted header byte.
- Two CRC-16/CCITT-FALSE bytes bound to the header, mode, and uncompressed body.

The 302 bare routes contain 60,686 transmitted bytes before text encoding. Contextual chat escaping adds **26 characters total**. Full-fidelity and no-names escaping add 30 and 21 characters respectively. Removing escaping or changing the alphabet is not a compatible wire optimization.

For scale only, deleting the two CRC bytes without replacing their protection would reduce the bare aggregate by 772 characters; deleting the header would reduce it by 405. These are counterfactual encodings, **not valid share codes**. They cannot be combined by simple addition because base-91 grouping and escape behavior depend on the complete byte stream. Removing CRC is rejected, and removing the header would remove the current version/kind/mode discrimination.

## Legal compression alternatives

`EnvelopeAudit` compares the existing bare-route Rice/quotient/direct selection against raw-DEFLATE candidates at levels 1–9 with default, filtered, and Huffman-only strategies. It uses the production `V10Transport.Outbound` ordering: actual complete escaped text, direct mode, payload length, then unsigned payload bytes.

`EnvelopeRichAudit` repeats the search on the existing selected general and compact semantic bodies. It deliberately preserves each kind's current semantic choice, including the compact no-names canonical body. This is a transport experiment, not an exhaustive search of every semantic packing candidate.

| Profile | Routes | Current chars / UTF-8 bytes | With 27 DEFLATE settings | Strictly shorter routes |
|---|---:|---:|---:|---:|
| Bare coordinates | 302 | 75,674 | 75,669 | 2 |
| Full fidelity | 302 | 93,723 | 93,722 | 1 |
| No names | 302 | 78,492 | 78,491 | 1 |

Adding only Huffman-only compression at level 9 saves four bare characters, zero full-fidelity characters, and one no-names character. Adding level-1/default or level-6/default alone saves nothing. Current direct mode wins 296 of 302 bare routes; only six use DEFLATE.

A diagnostic exhaustive sweep of each selected compressed stream's last byte also tried every alternative that the production bounded inflater accepted as exactly the original body. It saved no further characters. This is rejected experimental work, not a proposed padding policy.

The audit found three cases across its bare/full portfolios where selecting by binary size alone produces longer text than selecting by actual final transport. The production comparator already uses the correct final-text ordering. A new candidate must continue to use it.

No timing claim is made: these candidates were rejected by their negligible size benefit before any production-performance recommendation.

## Tiny-route costs

All compatible compression alternatives leave these results unchanged:

| Prefix points | Eligible routes | Aggregate chars / UTF-8 bytes | Mean complete code |
|---|---:|---:|---:|
| 1 | 302 | 4,467 | 14.79 |
| 2 | 302 | 5,859 | 19.40 |
| 3 | 302 | 6,638 | 21.98 |
| 5 | 293 | 7,858 | 26.82 |
| 10 | 271 | 10,480 | 38.67 |

The actual encoded count is one byte in these cases. One point at `(0,0,0)` costs 12 complete characters; one point at `(0,64,0)` costs 13. Two repeated zero points cost 13 characters, and repetition through ten points remains 13 because existing DEFLATE already removes it. Empty bare routes cost eight characters, although the external corpus contains no empty routes.

### Hypothetical count-in-header format

`TinyEnvelopeAudit` reserves a hypothetical wire version 11 exclusively for direct bare routes of 1–16 points. The low nibble contains 11 and the upper nibble contains `pointCount - 1`. The body retains the existing first-coordinate representation and direct Rice/quotient representation; the separate count byte disappears. CRC-16 remains intact. This version has no generic content-kind or compression-mode field, and **current released V10/legacy readers do not import it**.

The local test decoder checks canonical transport and CRC, reconstructs the ordinary count-bearing semantic body, and delegates to the production bounded bare-route reader. Every candidate round-trips its exact ordered integer coordinates, and every single-bit payload mutation tested is rejected. This does not constitute a complete new-version security or compatibility review.

| Sample | Current | Hypothetical format | Characters saved |
|---|---:|---:|---:|
| 1-point prefixes | 4,467 | 4,032 | 435 |
| 2-point prefixes | 5,859 | 5,490 | 369 |
| 3-point prefixes | 6,638 | 6,196 | 442 |
| 5-point prefixes | 7,858 | 7,455 | 403 |
| 10-point prefixes | 10,480 | 10,149 | 331 |
| Actual corpus routes with 1–16 points, 59 routes | 2,366 | 2,282 | 84 |

Using this hypothetical format only for the 59 eligible real routes would reduce the entire bare corpus from 75,674 to **75,590**, a **0.111%** saving. That gain does not justify a dedicated wire version here. Future coordinate-codec work may use a small-route assumption inside an explicitly versioned representation, but it must account for every discriminator and preserve coordinate bounds, exact reconstruction, and corruption detection.

## Existing compatibility coupling

`V10CompactRouteCodec.decode` requires equality with `canonicalNoNamesSemantic`. That method calls `selectNoNamesCandidate`, which chooses the Rice-versus-quotient semantic body using the shared transport compressor portfolio and final text ordering.

Consequently, changing `V10GeneralRouteCodec.selectCandidate` or changing the candidate portfolio inside the compact no-names selector can change what the decoder calls canonical. An older valid body can then be rejected if its body is no longer the local winner. This is a source-level compatibility hazard; this audit does not claim an observed regression on the supplied corpus.

Transport optimization *after* preserving the selected semantic body does not introduce that problem: V10 explicitly accepts any valid raw-DEFLATE stream with the same exact body and valid CRC. Any future change to the no-names body selection must first decouple body acceptance from exporter winner selection and add released-code compatibility fixtures. No decoder canonicality rule was relaxed in this audit.
