# Painter preview review

## Changes

The painter keeps its 256 × 256 rotating preview and face texture orientation. Its immutable paint snapshot was already cached; this change targets the raster work that runs when the rounded angle or paint changes.

- Cache the six faces as ABGR colors when the paint changes, removing checked paint access and channel conversion from each covered screen pixel.
- Reuse a Java pixel buffer and bulk-copy it to the existing `NativeImage`, replacing individual native writes for clearing, faces, and edges.
- Precompute per-triangle perspective factors, reusing one depth reciprocal for both texture coordinates.
- Cull faces using the camera-to-face vector appropriate to the existing perspective projection. The previous normal-only test also rasterized some back-facing faces; the depth buffer hid those faces in the inspected fixtures.
- Use elapsed monotonic time for rotation, so system clock adjustments do not move the preview abruptly.

Texture registration and release still belong to the painter screen. Reinitializing the same open screen reuses its texture; `removed()` releases it. The reusable pixel/color buffers add about 262 KiB of Java array storage while the painter is retained. No worker, global frame cache, or additional GPU texture was added.

## Verification

On September 4, 2026, the changed production classes and tests compiled against the cached Minecraft 26.2 classpath with Java 25. All six test methods in `WaypointPaintPreviewTextureTest` and `WaypointPainterScreenTest` passed in a standalone headless runner.

The raster test compares output against independently calculated ray/box intersections across 24 rotations. It checks exterior face selection, side/top orientation, perspective sampling, and surrounding transparency. Eligibility depends on expected geometry and texel boundaries, never on the rendered pixel color. Every rotation must compare more than 300 samples, including more than 100 painted interior samples. The second raster test checks unchanged-frame reuse, immediate recoloring, and removal of old silhouette/depth data after rotation.

A real `NativeImage` allocation also confirmed the bulk ABGR transfer reads back the intended RGB colors `123456` and `ABCDEF`. The supported cached 1.21.11 and 26.2 `NativeImage` APIs both expose the existing `getPointer()` method used by the transfer. Cross-target builds remain the release gate's responsibility.

Test cleanup removed the literal import-label assertion and the unrelated assertions about a newly constructed route's default getters. The apply-all test instead verifies that applying paint actually re-enables an existing disabled group. Existing cross-face copying, atlas navigation, and image-size validation coverage remains.

## CPU experiment

The durable experiment is `tools/preview-experiments/paint-preview/run.py`. It extracts the original raster from revision `1ea7d08`, replacing only GPU texture ownership/upload with a real `NativeImage`. The current raster also writes to a real `NativeImage`. Both sides therefore measure CPU rasterization and native image writes, with no GPU upload or running Minecraft client.

The fixture uses distinct face colors and asymmetric marks. Frames at 0, 15, 45, and 135 degrees were pixel-identical before and after. The script saves individual images and a labeled comparison sheet outside the repository.

Each timing run renders 1,800 changing-angle frames with unchanged paint, after 3,000 warmup frames. Nine runs alternate which implementation goes first. On this Apple silicon host with Java 25.0.2:

| Measurement | Baseline | Updated |
| --- | ---: | ---: |
| Median total for 1,800 frames | 238.957 ms | 121.710 ms |
| Median per frame | 132.754 µs | 67.616 µs |

The measured CPU portion decreased by 49.1%. An earlier independent run measured a 48.5% decrease. These measurements do not establish a Minecraft FPS improvement or GPU upload cost. At the existing approximately 30 changing-angle updates per second, the measured CPU savings are about 2 ms per second on this host.

To reproduce, first obtain a current Java 25 test runtime classpath, for example with the existing `writeCodecExperimentClasspath` Gradle task, then run from the repository root:

```sh
python3 tools/preview-experiments/paint-preview/run.py \
  --classpath build/reports/codec-experiment-classpath.txt \
  --java-home /path/to/jdk-25 \
  --baseline 1ea7d08 \
  --output /tmp/waypointer-paint-preview
```

The output directory contains the generated baseline source, compiled experiment classes, raw timing samples, and PNGs. The harness compiles the current production raster directly. It does not change tracked source or start a render device.

## Limits

These are software raster and native image checks. They do not verify a live Minecraft screen, GUI scaling, final display filtering, frame extraction/upload timing, or resource release during an interactive screen transition. The painter's full-texel mapping is preserved; the existing world/export renderer's center-inset texture-coordinate mapping was not changed in this slice.
