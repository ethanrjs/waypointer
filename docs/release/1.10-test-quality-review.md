# 1.10 test quality review

## Result and scope

The baseline at `1ea7d08` contains **1,795 test methods in 216 test-bearing Java files**, producing **1,798 JUnit invocations**: 1,794 ordinary `@Test` methods and one `@ParameterizedTest` with the four `Direction` values. There are no repeated or dynamic tests. The 200-, 1,000-, and corpus-sized loops inside individual tests do not inflate the JUnit count. `src/test` contains 221 Java files (five are support files without test annotations) and 14 fixture/resource files.

This curation removes **11 methods across nine files** and rewrites **six layout tests across four files** (eleven edited test files total), leaving **1,784 methods / 1,787 expected invocations** for this curation alone. All 216 test-bearing files remain. These counts exclude independent preview, renderer, and painter repairs in the same branch; the integrated JUnit report is the authoritative final execution count. Reducing the number by combining unrelated assertions, changing discovery, or adding skips would not reduce maintenance cost, so none of those changes were made.

The inventory covers every test source. Manual assertion-level review concentrated on low-value candidates, repeated scenarios, compatibility/resource boundaries, storage failures, and the UI tests most likely to mirror implementation. This is not a claim that every remaining assertion is equally strong. The largest groups contain substantial useful coverage: codecs (348 methods), configuration/storage (122), core route state (158), and screens (388, including preview/settings).

## P2: remaining focused improvements

These are concrete follow-up candidates, **not blanket deletion requests**. They remain because deleting their mixed assertions would lose useful checks or because the desired acceptance criterion requires a separate decision.

1. **Prove focus behavior through the real screen lifecycle.** The two removed reflection tests must not be presented as prior autofocus evidence. A useful replacement would initialize/rebuild the screen, type into the initial field, and verify retained focus/query; it should fail when the focus action is removed. This requires an appropriate Minecraft UI harness or interactive check, not a new test of method modifiers.
2. **Separate optimization experiment results from correctness criteria before changing benchmark tests.** `dungeon/data/V10DungeonBenchmarkTest.boundedCoordinatePortfolioAblationStaysWithLocalRaw` freezes a 200-case win count, and `finalWireBeatsExactWpdAcrossLockedDungeonWorkloads` freezes three exact encoded lengths. These are optimization acceptance checks rather than historical decode compatibility. If codec choices intentionally change, move the comparative/length assertions into an explicit experiment task while retaining semantic round trips and any documented size budget. Do not remove fixed codec vectors or silently skip a release criterion to make a new encoder green.
3. **Keep naming/ownership changes narrow.** The remaining three `ExportImportSliceScreenTest` methods cover selection priority, modifier-click selection, and singular/plural overflow text. They could move to the owning policy tests if those files are later reorganized, but a move alone offers no behavioral gain. Similar-looking default and migration cases should only be deleted after locating a stronger retained scenario, as done above.

## Coverage worth keeping

- **Historical compatibility and independent fixtures:** native golden vectors; V1–V9 fixed wires; V10 cross-language payload/coordinate hashes; current SkyHanni, Skyblocker, Skytils, Soopy/Firmament, Odin, and ChunkLogger formats. Round-trip tests with the current encoder complement these fixtures and do not replace them. `WaypointCodecGoldenVectorGeneratorTest` also pins generated output against a committed fixture; it is not simply an unanchored encode/decode tautology.
- **Hostile input and resource bounds:** invalid headers, CRC/padding/truncation, trailing bytes, coordinate overflow, point/byte limits, corruption fallback, and bounded decompression/import. Different rejected shapes exercise different parser entry paths. The timeout in `WaypointImportHardeningTest` is a hostile-input bound, not a speed benchmark; retain it.
- **Data preservation and side effects:** failed saves remain dirty and retryable; corrupt files are quarantined without overwriting prior data; future schemas block writes; publisher identity and install/publication registries preserve identity; folders, hidden colors, and explicit route kind survive reload; snapshots detach from later edits. Do not remove these because they share setup.
- **State transitions and real feature regressions:** route progression across disabled/current/subwaypoint boundaries, room/lobby transitions, command dispatch, import selection, async worker completion, publication/session failure handling, and settings lifecycle checks all have plausible product failures. Nearby cases often change the operation being exercised, not just a literal.
- **Translation and resource contracts:** `TranslationCatalogTest` scans source to find translation keys and verifies resource coverage/format placeholders. This catches missing shipped translations and is materially different from the deleted prose matcher. Pixel dimensions for supplied icon atlases protect the runtime texture slicing contract; those fixtures were preserved.
- **Opt-in tools:** nine `@EnabledIfSystemProperty` methods remain: `CatalogPublishPreparationTimingTest`, `CodecBenchmark`, `CodecRouteBenchmarkTest.routeSizeReport`, `ColeweightSmokeTest`, `V10GoldenRegeneration`, `V10LengthReport`, `V10LockedCorpusTest`, `V10ProductionTimingTest`, and `RendererSceneKeyTimingTest`. They are expected to be skipped without their explicit inputs and must not be cited as normal-CI benchmark/corpus evidence. The other two `CodecRouteBenchmarkTest` methods validate benchmark methodology and remain ordinary tests. None was newly disabled.
